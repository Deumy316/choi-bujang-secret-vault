# 탈환 작전실 검증 기록 절차

이 문서는 1~11단계 회귀 계획을 실제 실행 기록으로 바꾸는 절차입니다. 현재 저장소에는 공식 41종 공격의 개별 명세가 없으므로 `src/attack-check.mjs`의 자체 점검을 공식 41종으로 간주하지 않습니다. 공식 목록이 확인될 때까지 41종은 **명세 미확인·미실행**입니다.

## 기록 위치와 신뢰 경계

- 검증 계획과 현재 상태: `src/operations-verification.mjs`
- 인증된 읽기 전용 조회: `GET /api/operations/status`
- 화면: 로그인 후 탈환 작전실의 **1~11단계 통합 검증표**
- 실제 결과는 실행 증거가 생긴 뒤에만 별도 검토를 거쳐 반영합니다. 화면에는 결과를 입력하거나 통과로 바꾸는 기능이 없습니다.
- 로컬 단위 시험, 자체 점검, Production HTTP 실측, 공식 심판 결과는 서로 다른 근거입니다. 하나를 다른 환경의 통과 증거로 바꾸어 기록하지 않습니다.

## 실행 전 인증 준비

1. 검사할 커밋 전체 해시와 대상 환경(`local` 또는 canonical Production URL)을 먼저 기록합니다.
2. 정상 요청에는 전용 시험 계정과 서버가 승인한 기기를 사용합니다.
3. 금지 요청에는 별도 시험 계정·미승인 기기·존재하지 않는 시험용 자원만 사용합니다. 실제 사용자 자료와 운영 DB를 변조하지 않습니다.
4. JWT, 비밀번호, 쿠키, 서버 키는 증거 파일·화면·명령 기록에 넣지 않습니다.

## 정상 요청 기록

1. 검증표의 요청 이름·유형과 기대 결과를 확인합니다.
2. 인증된 시험 환경에서 요청 한 건만 실행합니다.
3. 실제 HTTP 상태 또는 판정 결과를 원문 응답에서 확인합니다.
4. 서버 응답에 실제 요청 ID가 있을 때만 기록합니다. 없으면 `미기록`으로 둡니다.
5. 서버가 제공한 확인 시각이 있으면 사용하고, 없으면 실행 도구가 응답을 받은 UTC 시각과 그 출처를 함께 기록합니다.
6. 실제 결과가 기대 결과와 같을 때만 `success`, 다르면 `failure`로 분류합니다.

## 금지 요청 기록

1. 소유권·기기 승인·추가 확인·자료 구역 등 하나의 거부 조건만 분명한 시험 요청을 사용합니다.
2. 거부 HTTP 상태 또는 `deny`·`step_up` 판정과 이유 코드를 확인합니다.
3. 응답에 보호 메모 본문이나 다른 사용자의 식별정보가 포함되지 않았는지도 확인합니다.
4. 요청이 허용되거나 결과를 입증할 수 없으면 성공으로 기록하지 않고 `failure` 또는 `unverifiable`로 남깁니다.

## 증거 정리와 검증

- 남길 수 있는 값: 시험 ID, 단계, HTTP 메서드와 템플릿 경로, 상태 코드·판정·이유 코드, 실제 요청 ID, UTC 확인 시각, 대상 환경, 커밋, 증거 출처.
- 제거할 값: Authorization 헤더, JWT, 쿠키, 비밀번호, API 키, 전체 사용자 UUID, 이메일, 메모 제목·본문, DB 행 원문.
- 근거에는 실행 명령 이름이나 HTTP 측정 기록 위치를 적고, 실제 대상 커밋·환경이 일치하는지 별도로 대조합니다.
- 요청 ID·시각·대상 환경·커밋 중 필요한 근거가 빠졌거나 원본 결과를 재검증할 수 없으면 `unverifiable`입니다.
- 수동으로 상태 문자열만 바꾼 기록은 공식 통과 근거가 아닙니다.

실패나 복원 게이트 불충족이 확인되면 후속 시험을 중단하고, 기존 데이터가 바뀌지 않았는지 먼저 확인합니다.
